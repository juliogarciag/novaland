# 0001 - Entity/component layer: bitECS with data definitions

Status: accepted. Date: 2026-11-06.

## Context

The sim must be plain TypeScript, headless, deterministic and serializable, and it will be extended for years by many agents working in parallel. Per-entity state has to be cheap to iterate, trivial to snapshot and impossible to confuse with static content.

## Decision

- `packages/sim` uses **bitECS** (0.4) for entities and queries.
- A **component holds numeric, mutable, per-entity state only**: one typed array per field, indexed by entity id. No strings, objects or references. The type system enforces this (`NumericStore` in `core/components.ts`).
- Components are declared with `defineComponent(name, create)`. The declaration is global; the **data store is per sim** (`sim.store(Component)`), so several sims can coexist in one process (tests, server rooms) without sharing arrays.
- **Static or rich data lives in definition files** keyed by a numeric `defId`: names, shapes, colours, speeds, and later sprites, stats and effects. Each feature owns `features/<feature>/defs.ts` and a block of 100 ids; `content/defs.ts` concatenates them into the registry and checks uniqueness. An entity points at its definition through the `DefRef.id` component. Definition ids are stable and never reused.
- Adding a new kind of thing that behaves like an existing kind is **a new data entry in that feature's defs file**, nothing else. New behaviour is a new feature folder with its own components, commands and systems.
- Content such as levels and tuning values is data too (`content/`), never hardcoded in systems.

## Consequences

- Snapshots are generic: every component field of every entity, plus physics and rng, with no per-feature serialization code (`core/snapshot.ts`).
- Views and servers read defs for anything non-numeric; the ECS stays small and fast.
- Entity ids are recycled by bitECS. Never store an entity id in long-lived data without checking it still exists.
- Component stores are sized to `sim.capacity` (+1: bitECS ids start at 1); `sim.createEntity()` guards it and command handlers check `sim.isFull` first.
- Snapshots sort entities, components and fields, so the hash is independent of attach order.
